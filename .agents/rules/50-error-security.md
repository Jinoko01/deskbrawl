# 오류·인증·보안

- 예상 가능한 입력·권한·연결 오류와 내부 장애를 구분한다. 빈 catch나 로그만으로 실패를 숨기지 않는다.
- UI는 입력값·맥락을 유지하고 실패 범위와 복구 행동을 알려준다. 렌더 오류는 적절한 Error Boundary로 격리한다.
- HTTP·Socket.IO·IPC 각각의 오류 형식을 계약으로 정하고 내부 예외를 안전한 code·message로 변환한다. 스택·SQL·비밀값을 반환하지 않는다.
- JWT는 서버에서 서명·허용 알고리즘·만료와 계약된 issuer·audience를 검증한다. 단순 decode는 인증이 아니다.
- REST Guards와 Socket.IO 연결·이벤트 인가를 각각 적용한다. 사용자 ID는 검증된 인증 컨텍스트에서 얻는다.
- 연결 후에도 토큰 만료·탈퇴·퇴장·권한 변경을 처리한다. 핸드셰이크 성공만으로 모든 이벤트를 허용하지 않는다.
- 초대 토큰은 범위·만료·사용 횟수·폐기 정책을 정하고 안전한 난수 또는 검증 가능한 서명을 사용한다. 일회용 토큰은 동시 사용에도 한 번만 소비되게 한다.
- 초대 토큰만으로 인증 세션이나 방 권한 전체가 부여된다고 가정하지 않는다. 가입·참여 시점에 대상과 현재 조건을 검사한다.
- refresh token 등의 지속 저장은 OS 보호 저장소·검증된 보안 저장 방식을 사용한다. localStorage·Zustand persist·평문 파일·일반 Tauri Store를 보안 저장소로 간주하지 않는다.
- access token·refresh 정책·보안 저장 구현은 대상 프로젝트 계약으로 확정한다. 재발급을 구현하면 single-flight·반복 제한·실패 시 세션 정리를 포함한다.
- VITE_ 환경 변수와 배포된 JS·Rust 바이너리는 비밀 보관 수단이 아니다. 서버 비밀키와 DB 자격 증명을 넣지 않는다.
- 운영 통신에는 HTTPS/WSS를 사용하고 CORS·Socket.IO origin 정책과 Tauri CSP를 실제 origin에 제한한다. CORS를 인가 수단으로 간주하지 않는다.
- 입력 길이·payload 크기·이벤트 빈도·방 참여 권한을 서버에서 제한한다. 사용자 입력 HTML·파일 경로·URL·쉘 인자를 그대로 실행하지 않는다.
- 로그에는 requestId·roomId·tick 등 필요한 문맥만 남긴다. JWT·초대 토큰·개인정보·전체 payload를 기록하지 않는다.
