# 정보 구조 만들기

정보가 잘 구조화되어 있으면 독자는 적은 노력으로 내용을 이해한다. 문제는 글을 쓰는 입장이 되면 독자가 알고 싶은 것보다 내가 말하고 싶은 것을 중심으로 구조를 짜게 된다는 점이다. 아래 다섯 원칙은 그 편향을 교정하기 위한 것이다.

---

## 1. 한 페이지에서 하나만 다루기

한 문서에 너무 많은 내용을 담으면 독자가 핵심을 파악하기 어렵고, 나중에 수정하기도 어려워진다. 중복된 내용이 여러 문서에 흩어지기도 한다.

**제목 깊이가 `####`(H4)에 도달하면 문서를 나눌 신호다.** `###`(H3)까지는 유지할 수 있다.

**Don't** — "React 사용법"은 주제가 너무 넓다. 깊은 제목이 등장하는 것이 분리 신호다.

```markdown
# React 사용법

## 컴포넌트 생성

### 컴포넌트 기본 구조

#### JSX 사용법

##### JSX 문법 세부사항

## 상태 관리

### 상태 정의

#### useState 사용법
```

**Do** — 하나의 목표만 다룬다. 개별 개념을 지나치게 파고들지 않는다.

```markdown
# React 컴포넌트 생성하기

## 컴포넌트 기본 구조

## 상태 관리

## 라이프사이클 메서드
```

여러 개념을 개략적으로 소개해야 하면 개요 페이지를 따로 만들고 각 항목을 별도 문서로 링크한다. 한 페이지에서 두 개 이상의 핵심 주제를 다루고 있다면 분리한다.

---

## 2. 가치를 먼저 제공하기

독자는 "이 기능이 왜 필요한가", "내게 어떤 도움이 되는가"를 먼저 알고 싶어 한다. 기능이나 세부 설정보다 그 기능이 해결하는 문제와 제공하는 가치를 먼저 전달한다.

|       | 문장                                                                                                |
| ----- | --------------------------------------------------------------------------------------------------- |
| Don't | 리버스 프록시 설정은 2019년에 도입되었고, 많은 수정이 있었습니다                                    |
| Do    | 리버스 프록시 설정을 적용하면 네트워크 지연 문제를 최소화할 수 있어요                               |
| Don't | 이 스니펫은 다양한 설정 옵션을 제공합니다. 먼저 `connection_timeout`, `retry_attempts`를 수정하세요 |
| Do    | 이 스니펫을 사용하면 PostgreSQL 데이터베이스 연결 속도가 50% 빨라집니다                             |

부가 정보와 세부 사항은 뒤로 미룬다.

## 3. 효과적인 제목 쓰기

제목이 명확하면 독자가 문서를 빠르게 스캔할 수 있고, 검색에서도 찾기 쉬워진다.

**핵심 키워드를 넣는다.**

|       | 제목                                                      |
| ----- | --------------------------------------------------------- |
| Don't | `# 에러를 해결하는 방법은?` — 무슨 에러인지 추측해야 한다 |
| Do    | ``# `NOT_FOUND_USER` 에러를 해결하는 방법``               |

**같은 수준의 제목은 문체를 통일한다.** 동사형이든 명사형이든 하나로 맞춘다.

|       | 제목 목록                                                              |
| ----- | ---------------------------------------------------------------------- |
| Don't | `## 키워드를 포함하세요` / `## 일관성 유지` / `## 평서문으로 작성하기` |
| Do    | `## 키워드 포함하기` / `## 일관성 유지하기` / `## 평서문으로 작성하기` |

**그 외**

- 30자 이내로 쓴다. 중복되거나 불필요한 단어를 덜어낸다.
- 평서문으로 쓴다. `!`와 `?`는 쓰지 않는다.
- 단계별 절차를 다루는 문서라면 제목에 숫자를 넣는다.

## 4. 예측 가능하게 하기

예측 가능한 문서는 일관된 용어와 표현을 쓰고, 설명의 흐름이 자연스럽게 연결되며, 새로운 정보가 논리적 순서로 배치된다.

### 일관된 위계를 유지한다

**Don't** — 섹션 간 위계가 불규칙하다. `### API 속도 측정`이 성능 향상 기법의 하위 항목인지 알 수 없다.

```markdown
## 성능 향상 기법

- 캐싱 활용하기
- 요청 병합하기

### API 속도 측정

## 오류 처리
```

**Do** — 같은 수준의 개념을 같은 위계로 정리한다.

```markdown
## 1. 성능 향상 기법

### 캐싱 활용하기

### 요청 병합하기

## 2. API 속도 측정

## 3. 오류 처리
```

### 섹션 제목은 문서 전체에서 같은 패턴을 따른다

한 문서에서 "설치", 다른 문서에서 "환경 설정"이라고 부르면 독자는 두 섹션이 같은 내용인지 헷갈린다. 통일된 섹션 이름과 순서를 유지한다.

### 설명이 코드보다 먼저 온다

**Don't**

````markdown
## API 요청 예제

```js
fetch("https://api.example.com/data").then((response) => response.json());
```

이 코드는 서버에서 데이터를 가져와 JSON으로 변환합니다.
````

**Do**

````markdown
## API 요청 예제

서버에서 데이터를 가져와 JSON으로 변환하는 방법을 알아봅니다.

```js
fetch("https://api.example.com/data").then((response) => response.json());
```
````

### 논리적인 순서로 배치한다

핵심 개념 → 구체적인 사용법 → 예제 코드 → 심화 내용 순으로 쌓아 올린다.

|       | 목차                                                                           |
| ----- | ------------------------------------------------------------------------------ |
| Don't | `## 비동기 데이터 요청하기` → `## 기본적인 사용법` → `## 클린업 함수 활용하기` |
| Do    | `## 기본적인 사용법` → `## 비동기 데이터 요청하기` → `## 클린업 함수 활용하기` |

### 용어를 일관되게 쓴다

|       | 문장                                                                                                                             |
| ----- | -------------------------------------------------------------------------------------------------------------------------------- |
| Don't | 컴포넌트 내부에서 **데이터 저장**을 위해 `useState`를 사용합니다. **값 유지**가 필요할 때는 `useReducer`를 고려하세요            |
| Do    | 컴포넌트 내부에서 **상태를 저장**하기 위해 `useState`를 사용합니다. 더 **복잡한 상태 관리**가 필요하면 `useReducer`를 고려하세요 |

"Error Handling"과 "오류 처리"를 섞어 쓰지 않는다. 주요 개념은 용어 사전을 만들어 두고 일관되게 적용한다.

## 5. 자세히 설명하기

독자는 이 문서를 처음 읽는다. 이해에 꼭 필요한 정보를 생략하면 독자가 스스로 추론해야 하므로 오해가 생기고 인지 부담이 늘어난다.

### 새 개념은 한두 문장으로 정의한다

|       | 문장                                                                                                                                                                          |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Don't | 이 서비스는 이벤트 소싱 방식을 사용해 상태를 관리합니다                                                                                                                       |
| Do    | 이 서비스는 이벤트 소싱(Event Sourcing) 방식을 사용해 상태를 관리합니다. 이벤트 소싱은 상태의 최종 결과만 저장하는 대신, 상태 변화를 일으킨 모든 이벤트를 기록하는 방식입니다 |

필요하면 이 개념을 왜 알아야 하는지, 어디에서 쓰는지도 함께 안내한다.

### 동작 조건과 단위를 밝힌다

**Don't**

```
sessions[].duration: 세션의 지속 시간을 나타냅니다.
```

지속 시간이 어떻게 결정되는지, 단위가 무엇인지 알 수 없다.

**Do**

```
sessions[].duration: 세션의 지속 시간으로, 사용자가 로그인을 유지한 시간입니다.
수동 로그아웃으로 종료된 경우 실제 이용 시간을 나타냅니다.
시간 초과로 자동 종료되었다면 마지막 활동 시점까지의 시간을 나타냅니다.
단위는 밀리초(ms)입니다.
```

입력값·상태·시간에 따라 결과가 어떻게 달라지는지 구체적으로 설명하면 오해를 막을 수 있다.

## 개요 빠트리지 않기

개요는 독자가 문서를 끝까지 읽을지 결정하는 요소이고, 검색 결과에 노출되는 부분이기도 하다. 개요를 먼저 쓰면 글을 쓰는 동안 초점을 유지하는 데도 도움이 된다.

**제목 바로 아래, 본문이 시작되기 전에 배치한다.** "이 문서를 읽으면 무엇을 할 수 있는가"에 답해야 한다.

|       | 개요                                                                                                                                                                       |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Don't | 이 문서는 TypeScript의 유틸리티 타입을 소개합니다. `Partial`, `Pick`, `Omit` 등을 사용할 수 있어요 — 왜 써야 하는지가 없다                                                 |
| Do    | 유틸리티 타입을 활용하면 반복적인 타입 선언을 줄이고 더 유연하게 타입을 관리할 수 있어요. 이 문서에서는 `Partial`, `Pick`, `Omit`으로 객체 타입을 다루는 방법을 알아볼게요 |
| Don't | React에서 상태 관리란 무엇일까요? React는 컴포넌트 기반 UI 라이브러리로... — 길고 추상적이다                                                                               |
| Do    | 이 문서는 React 상태 관리의 개념과 주요 기법을 설명합니다. `useState`, `useReducer`, Context API, Redux를 비교하고 각 방식의 장단점을 정리합니다                           |

기술적 배경 설명보다 독자가 얻을 직접적인 가치를 먼저 쓴다.
