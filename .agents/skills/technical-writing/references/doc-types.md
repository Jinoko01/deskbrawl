# 문서 유형 정하기

독자의 목적에 따라 기술 문서를 네 가지로 나눈다. 유형을 먼저 정하면 어떤 정보를 어떤 순서로 담을지가 거의 결정된다.

| 유형      | 독자의 목적                                         | 예시                         |
| --------- | --------------------------------------------------- | ---------------------------- |
| 학습 중심 | 처음 접하는 기술의 흐름을 익히고 싶다               | 시작하기, 튜토리얼           |
| 문제 해결 | 배경 지식은 있고, 특정 문제나 작업을 처리하고 싶다  | How-to 가이드, 트러블슈팅    |
| 참조      | 사용법은 알고, 특정 API의 세부 정보를 확인하고 싶다 | API 레퍼런스, 에러 코드 목록 |
| 설명      | 개념·원리·배경을 깊이 이해하고 싶다                 | 아키텍처 설명, 도메인 문서   |

유형을 조합해도 된다. 예를 들어 튜토리얼 앞부분에 개념 설명을 조금 섞을 수 있다. 다만 한 문서의 중심 유형은 하나여야 한다.

## 유형 판단 기준

독자가 던질 질문을 그대로 옮겨 보면 유형이 드러난다.

- "이 기술을 어떻게 시작하지?" → 학습 중심
- "X를 하려면 어떻게 설정하지?" → How-to 가이드
- "이 에러는 왜 나고 어떻게 고치지?" → 트러블슈팅
- "이 에러 메시지가 무슨 뜻이지?" → 참조(에러 코드 문서)
- "이 함수의 파라미터가 뭐지?" → 참조
- "왜 이런 방식으로 동작하지?" → 설명

트러블슈팅과 에러 코드 문서의 차이: 에러 코드 문서는 뜻을 찾는 사전이고, 트러블슈팅은 해결 절차를 담는 가이드다.

시작하기와 튜토리얼의 차이: 시작하기는 전체 흐름과 필수 개념을 훑는 문서, 튜토리얼은 명확한 결과물을 만들며 개념을 익히는 문서다.

How-to 가이드와 트러블슈팅의 차이: 가이드는 특정 기능을 구현하는 데, 트러블슈팅은 이미 발생한 문제를 진단하는 데 초점이 있다.

## 1. 학습 중심 문서

**원칙**

- 처음부터 끝까지 막힘없이 따라갈 수 있어야 한다. 모든 예제 코드를 실제로 실행해 검증한다.
- 단계별로 설명한다. 예제는 쉬운 것부터 점진적으로 어렵게 배치한다.
- 실행 가능한 코드 예제를 넣는다. 각 단계에서 기대할 결과도 알려줘야 독자가 성공 여부를 스스로 확인할 수 있다.

**분량이 길어질 때**: 본문은 성공 경로만 남기고, 자주 겪는 문제는 문서 끝의 FAQ 섹션으로 빼거나 접히는 컴포넌트에 넣는다.

**체크리스트**

- [ ] 학습 목표를 명확하게 제시했는가
- [ ] 직접 따라 했을 때 오류가 나지 않는가
- [ ] 단계별로 설명되어 있는가
- [ ] 독자가 직접 실행할 수 있는 코드 예제가 있는가

**템플릿**

```markdown
# [튜토리얼 제목]

## 목표

[이 튜토리얼을 따라하고 나면 독자가 달성할 목표]

## 사전 요구사항

- [필요한 사전 지식, 설치할 도구. 없으면 생략]

## 단계별 가이드

### [첫 번째 단계 제목]

[이 단계에서 할 작업 + 코드 예제 또는 화면 캡처]

### [두 번째 단계 제목]

[다음 단계에서 할 작업]

### 최종 결과 확인

[목표를 달성했을 때 어떤 결과가 나오는지]
```

## 2. 문제 해결 중심 문서

**원칙**

- 문제 상황을 명확히 정의한다. 원인과 그로 인해 나타난 현상을 구분해서 쓴다. 에러 메시지와 로그 예시를 넣는다.
- 바로 적용할 수 있는 해결 방법을 제공한다. 코드, 명령어, 설정을 포함하고 그 방법이 왜 문제를 해결하는지도 밝힌다.
- 환경별 차이를 다룬다. OS, 라이브러리 버전에 따른 차이를 설명한다.
- 해결 후 정상 동작을 확인하는 방법까지 넣는다.

**체크리스트**

- [ ] 원인만 설명하지 않고, 에러에 대한 배경 지식도 제공했는가
- [ ] 즉시 적용할 수 있는 해결 방법이 있는가
- [ ] 환경별(OS, 버전) 차이를 고려했는가
- [ ] 문제가 해결됐는지 확인하는 방법이 있는가

**템플릿**

```markdown
# [문제 해결 문서 제목]

## 문제 정의

[독자가 겪을 수 있는 문제 상황]

## 사전 요구사항

[필요한 환경 설정이나 필수 조건. 없으면 생략]

## 해결 방법

### [첫 번째 해결 방법]

### [두 번째 해결 방법]

### 문제 해결 후 확인 방법

[문제가 해결된 후의 모습이나 확인 방법]
```

## 3. 참조 문서

**원칙**

- 정확성과 완전성이 우선이다. 누락이나 모호한 설명이 없어야 하고 항상 최신 상태를 유지한다.
- 일관된 구조로 쓴다. 이름 → 시그니처 → 매개변수 → 반환값 → 예제 순서를 문서 전체에서 지킨다.
- 검색과 탐색이 쉬워야 한다. 목차와 앵커 링크를 제공한다.
- 예제 코드를 함께 준다.
- API 키 설정, 인증 방식처럼 사전에 알아야 할 정보는 문서 앞부분에 배치한다.

**체크리스트**

- [ ] 검색·탐색이 쉬운 구조인가
- [ ] 정보가 정확하고 완전한가
- [ ] 일관된 구조와 형식인가
- [ ] 실용적인 예제 코드가 있는가

**템플릿**

```markdown
# [참조 문서 제목]

## 개요

[이 요소가 무엇이며 언제 쓰고, 어떤 가치를 주는지]

## 속성 및 옵션

| 속성명 | 타입   | 기본값    | 설명 |
| ------ | ------ | --------- | ---- |
| prop1  | string | "default" | ...  |

## 시그니처

[코드]

## 반환값

[반환하는 값]

## 사용 예제

[구체적인 상황 + 예제 코드]
```

## 4. 설명 문서

**원칙**

- 배경과 맥락을 먼저 준다. 이 기술이 등장한 이유와 해결하려는 문제부터 설명하고, 독자가 왜 이걸 선택해야 하는지 납득하게 만든다.
- 시각 자료를 적극적으로 쓴다. 구조, 데이터 흐름, 컴포넌트 관계는 다이어그램이나 표로 보여준다.
- 사용법을 넘어 원리와 설계 의도를 이해할 수 있게 한다.

**체크리스트**

- [ ] 핵심 원리와 배경이 명확한가
- [ ] 복잡한 개념을 시각화했는가
- [ ] 선행 지식을 충분히 안내했는가

**템플릿**

```markdown
# [개념명]

## 개념 소개

[이 개념이 무엇인지]

## 등장 배경

[왜 등장했는지, 어떤 문제를 해결하는지]

## 활용

[실제 프로젝트에서 어떻게 쓰이는지]
```

## 문서 트리

여러 페이지로 구성할 때는 유형별로 디렉토리를 나눈다. 정답이 있는 구조는 아니므로, 독자에게 어떤 문서가 필요한지부터 생각한다.

```
docs/
├── get-started.md
├── tutorials/        # 학습 중심 문서
│   ├── a-tutorial.md
│   └── another-tutorial.md
├── how-tos/          # 문제 해결 중심 문서
│   ├── a-how-to.md
│   └── another-how-to.md
├── explanations/     # 개념 설명 문서
│   ├── a-concept.md
│   └── a-topic.md
├── reference/        # 참조 문서
│   ├── an-element.md
│   └── another-element.md
├── troubleshooting.md
└── glossary.md
```

특정 주제 하나를 다룰 때는 개요 → 기본 개념 → 튜토리얼 → 목표별 가이드 → 문제 해결 순으로 배치한다.

```
nextjs-performance-optimization/
├── index.md                  # 개요
├── fundamentals.md           # 기본 개념
├── tutorial.md               # 간단한 튜토리얼
├── guides/
│   ├── code-splitting.md
│   ├── image-optimization.md
│   └── caching-strategies.md
└── troubleshooting.md
```

**크로스링크**: 튜토리얼에서 간단히 넘긴 내용은 가이드나 참조 문서로 링크한다. 독자가 더 깊은 정보가 필요한 순간에 바로 찾아갈 수 있어야 한다.

- 학습 문서는 개요 → 실습 → 심화처럼 계층을 가질 수 있다.
- 문제 해결 문서와 설명 문서는 계층 없이 같은 레벨로 나열해도 된다.
- 참조 문서는 별도 페이지에서 목록을 제공한다.
