# TypeScript와 구조

- strict 기준으로 작성하고 any·non-null assertion·타입 오류 억제로 검증을 우회하지 않는다. 외부 값은 unknown에서 검증해 좁힌다.
- 공유 wire 타입은 Zod 스키마에서 추론한다. TypeScript 타입이나 Socket.IO 제네릭만으로 런타임 검증을 대체하지 않는다.
- Prisma 모델, 서버 내부 모델, 외부 DTO, 화면 모델은 역할이 다르면 분리한다. DB 모델을 그대로 클라이언트 계약으로 export하지 않는다.
- 제한된 상태는 판별 유니온으로 표현한다. 함수·props·모듈 경계는 입력·반환과 실패 동작이 드러나게 한다.
- 도메인 전용 Hook·유틸·타입은 해당 도메인 가까이 둔다. 실제 재사용이 확인된 경우에만 공통화한다.
- 여러 화면에서 쓰는 UI는 공통 components에, 페이지 전용 하위 UI는 해당 페이지의 components에 둔다. 짧은 파일 내부 컴포넌트를 무조건 파일로 나누지 않는다.
- NestJS는 도메인 모듈 단위로 구성한다. 모든 서비스에 기계적으로 repository·interface·factory를 추가하지 않는다.
- 서버·클라이언트는 공유 프로토콜에 의존하고 서로의 구현을 import하지 않는다. 순환 의존을 만들지 않는다.
- 주석은 규약·단위·경계·우회할 수 없는 제약과 비자명한 선택의 이유를 설명한다. Rust unsafe의 안전 조건은 반드시 남긴다.
- 프레임워크가 요구하지 않는 전역 싱글턴과 모듈 import 시 실행되는 연결·타이머를 피한다.
