# 서버 비용 3단계 실행 기록 — 인증 DB 반복 조회 줄이기

작성일: 2026-11-05 · 상태: 구현·로컬 검증 완료, Windows 실기기 확인 전

[로드맵 6절](server-cost-roadmap.md#6-단계-3--인증-조회-줄이기)의 3단계를 구현했다. 2단계(활동 중 10Hz 전송)는 화면 끊김으로 롤백했으므로, 이 기록은 1단계까지 반영된 코드를 기준으로 한다.

## 1. 확정한 정책

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| JWT | 유지. `exp`를 연결 컨텍스트의 만료 시각으로 사용 | 비용 원인은 JWT가 아니라 반복 DB 조회. 제거 시 의존성·설정·토큰 의미 변경만 생김 |
| 연결 중 장치 폐기 반영 | 최대 약 1초(매초 묶음 조회) 허용 | 2026-11-05 사용자 승인. 서버 코드에 `revokedAt`을 설정하는 경로가 없어 폐기는 운영자 DB 수정으로만 발생 |
| 명령과 폐기 동시 발생 | 확인 전에 수락된 명령은 처리, 다음 확인에서 연결 종료 | 위 1초 허용의 직접적인 결과 |
| 묶음 조회 중 DB 장애 | 기존 연결은 서명 검증된 토큰이 만료될 때까지 유지, 경고 로그는 장애 시작 시 1회. 새 연결은 지금처럼 DB 확인 필요 | 이전에는 DB 장애 시 모든 연결이 1초 안에 끊기고 모든 명령이 실패 |
| 토큰 만료 | DB와 무관하게 명령마다 `exp`로 거부, 1초 안에 연결 종료 | 기존 의미 유지 |

## 2. 변경 내용

| 파일 | 변경 |
| --- | --- |
| [auth.service.ts](../apps/server/src/modules/auth.service.ts) | 서명·클레임 검증(`verifyToken`)과 DB 확인을 분리. `authenticate()`는 `{ deviceId, expiresAt }` 반환, `inactiveDevices()`는 장치 ID 목록의 폐기·삭제 여부를 `findMany` 1회로 확인. 기존 `verify()`(REST `DeviceGuard`)의 의미는 동일 |
| [visits.gateway.ts](../apps/server/src/modules/visits.gateway.ts) | 핸드셰이크 인증 결과를 `WeakMap<Socket, AccessClaims>`에 보관. 명령은 DB 없이 만료만 확인. 매초 타이머는 만료를 메모리에서 확인하고 폐기는 묶음 조회 1회로 확인. 이전 조회가 끝나지 않았으면 해당 주기를 건너뜀 |
| [visits.integration.cjs](../apps/server/test/visits.integration.cjs) | 명령 20회 동안 장치 조회 0회, 연결 중 폐기 시 2.5초 안에 종료되고 재연결 거부(다른 장치는 유지), 짧은 만료 토큰은 `exp` 이후 종료되고 재연결 거부, 묶음 조회가 실패해도 기존 연결의 명령 처리 유지 |
| [cost-benchmark.cjs](../apps/server/test/cost-benchmark.cjs) | `revokedAt`을 선택하는 `findMany`도 인증 조회로 계수(묶음 1회 = 1) |

## 4. 전후 측정

같은 장비(Intel Core Ultra 9 185H, Node v24.14.0)와 같은 Docker PostgreSQL 전용 컨테이너로, 0단계 조건(준비 3초 제외, 10초×3회, 추가 활동 120초, 방 재생성 5회, 종료 후 65초)에서 실행했다. 두 실행 모두 `COST_BENCH_IDLE_SNAPSHOTS=1`, `health: true`다. 아래 표의 값은 3회 평균이며, 로컬 loopback 측정이라 운영 수치가 아니다.

3개 방 120초 연속 활동: 인증 조회 216.90→0.99/s, 서버 CPU 18.80→6.76%, 입력 ack p95 19.54→3.28ms. 재접속(같은 world 복구·이전 visit 거부)과 방 재생성 후 정리는 양쪽 모두 성공했고, 실패한 명령은 0건이었다.

해석:

- 인증 조회가 입력 빈도·연결 수와 무관하게 **연결이 있는 동안 초당 약 1회**로 고정됐다. 로드맵의 완료 기준인 "입력 빈도가 늘 때 인증 DB 조회가 같은 비율로 증가하지 않음"을 충족한다.
- 활동 상태에서 서버·DB CPU와 입력 ack 지연이 함께 줄었다. ack는 수락 응답 시간이며 화면 반응 시간이 아니다.
- 1인 대기는 원래 초당 방 수만큼 조회했으므로 1개 방에서는 차이가 없다. 대기 상태의 1% 내외 CPU 값은 측정 잡음 범위라 개선·악화로 해석하지 않는다.
- 소켓 송신량은 변하지 않았다. 이 단계는 송신량 대상이 아니다.
- 반복 측정은 각 1회 실행(구간별 3회 반복)이며, 서버 RSS 차이는 프로세스 실행 간 차이를 배제하지 못해 결과로 보고하지 않는다.

## 5. 남은 제한

- Windows 실기기에서 데스크톱 앱으로 장시간 연결·재연결·토큰 만료 동작을 확인하지 않았다. 확인 전까지 단계 완료를 보류한다.
- 연결 중인 장치가 매우 많을 때 `id IN (...)` 한 번의 크기 제한·분할은 운영 수용량이 정해진 뒤 검토한다(TBD).
- 장치 폐기를 실제로 수행하는 API·관리 기능은 없다. 범위 밖이다.
- 문제가 생기면 Gateway의 `command()`와 매초 타이머를 `AuthService.verify()` 호출로 되돌리면 된다. DB·계약 변경이 없어 서버 코드만 되돌리면 된다.
