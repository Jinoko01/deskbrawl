# DeskBrawl 서버 비용 절감·오픈소스 운영 계획

작성일: 2026-11-01 · 상태: 0단계 로컬 기준선·후보 공시요금 확인 완료, 월 예산·운영 상한 미정

목표는 기본 사용 경험을 유지하면서 초기 고정비와 사용량에 따른 비용 증가를 줄이고, 자체 서버와 유료 공식 호스팅을 함께 제공할 기반을 만드는 것이다. 이 문서는 작업 계획이며 구현·성능 개선·배포가 완료되었다는 의미가 아니다.

## 1. 진행 순서와 기준

| 단계 | 목적 | 선행 조건 | 결과물 |
| --- | --- | --- | --- |
| 0 | 비용과 성능 기준선 측정 | 현재 구현 | 상태별 부하·비용 산정표 |
| 1 | 대기 중 불필요한 전송 축소 | 0 | 변화가 없는 방의 송신량 감소 |
| 2 | 플레이 중 전송 빈도 최적화 | 1 | 20Hz·10Hz 비교 결과와 채택값 |
| 3 | 인증 DB 반복 조회 축소 | 0, 공개 전 1·2 결과와 통합 검증 | 인증 의미를 유지한 조회 감소 |
| 4 | 작은 단일 서버로 제한 베타 | 1~3, 공개 준비 | 운영비·수용량·장애 복구 기록 |
| 5 | 일반 사용자용 셀프호스팅 지원 | 4에서 호환·운영 기준 확보 | 재빌드 없이 자체 서버 연결 |
| 6 | 공식 호스팅 수익성 검증 | 4의 실사용 비용, 5의 기본 지원 | 무료·유료 범위와 수익성 판단 |

0~3을 초기 구현 범위로 삼고, 4는 배포 승인 후 진행한다. 5~6의 제품 정책은 별도 확정한다. 일정과 단계별 소요 기간은 **TBD**이며, 앞 단계의 완료 기준을 충족한 뒤 다음 단계로 넘어간다.

공개 전에는 중앙 서버가 게임 판정을 맡는 현재 경계를 유지한다. NestJS 교체, Redis, 여러 지역 배치, 복수 게임 서버, 바이너리 프로토콜은 실측으로 필요성이 확인되기 전에는 도입하지 않는다.

## 2. 현재 확인된 사실과 미정 항목

- 서버는 50ms 고정 tick으로 계산하고, 집중 모드가 아닌 방은 tick마다 전체 스냅샷 전송 경로를 실행한다. 참가자가 호스트 한 명인 경우도 포함된다.
- 게임 명령마다 인증 과정에서 장치 폐기 여부를 DB로 조회하며, 연결별 인증 확인도 매초 수행한다.
- 게임 상태와 최신 채팅은 서버 메모리에 있고, PostgreSQL에는 장치·방·초대 데이터가 있다. 서버 재시작 시 월드는 복구되지 않는다.
- 로컬 게임은 이미 있지만 온라인 방에서 로컬 게임으로 판정을 넘기는 기능이 완성되어 있다는 뜻은 아니다.
- 자체 서버 주소는 현재 `network:config`로 빌드 시 지정한다. 일반 사용자가 배포 앱에서 서버를 선택하는 기능은 별도 작업이다.
- [기존 측정](m4-server-measurements.md)은 Windows에서 6인 방 하나를 짧게 실행한 결과다. 정상 구간 평균 스냅샷은 3,089.52 bytes, 서버 프로세스의 관측 최대 RSS는 약 140MiB였다. 방당 추가 메모리나 운영 수용량을 의미하지 않는다.

채택할 서버 사업자·월 예산·공개 인원·보장 지연·운영 수용량은 **TBD**다. 2026-11-01 확인한 후보 공시요금과 가정 견적은 [0단계 실행 기록](server-cost-stage0.md)에 구분해 남겼다.

## 3. 단계 0 — 측정과 비용 기준선

2026-11-01 실행 기록: [상태·방 수별 측정 및 비용 산정표](server-cost-stage0.md)와 [원본 JSON](measurements/server-cost-stage0-2026-11-01.json). 빈 서버·1인 대기·6인 대기·6인 활동을 1·2·3개 방에서 측정했다. 재접속·120초 추가 활동·5회 방 재생성·종료 후 정리도 확인했다. AWS 후보의 공시요금 기반 견적을 추가했으나 실제 운영 견적·베타 월 예산·신규 입장 상한은 TBD이며, 0단계 전체 완료로 표시하지 않는다.

**할 일**

- [기존 벤치마크](../apps/server/test/m4-benchmark.cjs)를 바탕으로 방 수와 참가자 수를 바꿀 수 있는 측정을 준비한다. 기존 스크립트는 단일 6인 방과 구간당 최대 30초를 전제로 하므로 다중 방·장시간 검증에는 확장이 필요하다.
- 빈 서버, 혼자 대기, 6인 대기, 6인 이동·공격·투척·채팅을 각각 측정한다. 다중 방은 1개에서 시작해 점진적으로 늘린다.
- 동일 장비·동일 입력 조건에서 준비 구간을 분리하고 반복 측정한다. 장시간 연결·방 생성/종료 후 자원이 남는지도 확인한다. 반복 횟수·지속 시간은 실행 계획에 기록한다.
- 서버·DB의 CPU와 메모리, 인증 조회 수, tick 실행 시간과 밀림, 실제 송신 바이트, 입력 ack 지연, 재연결 결과를 기록한다. 클라이언트 부하와 서버 부하를 분리한다.
- 운영 후보의 컴퓨팅·DB·포함 트래픽·초과 송신·백업·로그 비용을 실제 견적으로 채운다. 베타 월 예산과 신규 입장 제한 기준을 정한다.

**완료 기준**

- 상태·방 수별 재현 조건과 원본 결과가 있고, 이후 변경과 비교할 수 있다.
- 실제 송신량과 JSON payload 추산을 구분한다. 입력 ack를 화면 반응 시간으로 보고하지 않는다.
- 월 예산과 과금 구조가 정해지기 전에는 운영 용량·월 비용을 확정하지 않는다.

## 4. 단계 1 — 대기 중 전송 줄이기

[1단계 실행 계획](server-cost-stage1-plan.md)을 2026-11-03 작성했다. 선택적 연결 capability, 시간 효과·입력 sequence 보존, 정지 후 보간 보정, 호환성·전후 측정을 포함한다. 2026-11-04 구현·로컬 검증을 마쳤고 [실행 기록](server-cost-stage1.md)에 전후 측정을 남겼다. 대기 상태 정기 송신은 지원 연결에서 100% 줄었으며, Windows 실기기 화면 확인 전이라 단계 완료는 보류한다.

**할 일**

- 먼저 계산 주기는 유지하고, 바뀐 상태가 없는 방의 반복 스냅샷 전송을 생략한다. 매 tick 증가하는 값만으로 변화 여부를 판단하지 않도록 기준을 정한다.
- 이동·공격·돌·넉백·기절·효과·채팅·프로필·멤버 변경을 전송 판단에 포함한다. 입력 적용 sequence의 갱신도 누락하지 않는다.
- 새 참가자 입장·재접속에는 전체 스냅샷을 보내고, 연결 확인·토큰 만료·단절 유예 처리는 계속한다.
- 클라이언트가 스냅샷 수신을 연결 상태 판단이나 시간 진행에 사용하는지 확인하고, 긴 대기가 연결 끊김으로 오인되지 않도록 한다.
- 전송 생략 효과가 부족할 때만 유휴 방의 계산 생략을 후속 검토한다. 이때 쿨다운·효과·채팅 만료와 깨어난 직후의 시간 진행을 먼저 명세한다.

**완료 기준**

- 같은 대기 시나리오의 송신량이 기준선보다 감소한다. 감소율은 실측값으로 기록한다.
- 정지 후 첫 입력, WORK 드래그, 채팅 만료, 신규 입장, 재연결, 집중 모드·강퇴가 정상 반영된다.
- 구버전 앱도 검증한다. 호환 동작을 바꾸어야 한다면 기능 협상 또는 계약 버전 변경안을 먼저 작성한다.

혼자 있는 온라인 방은 이 단계에서 서버 판정을 유지한다. 이를 로컬 게임으로 전환하는 작업은 아래의 조건부 후속 과제로 분리한다.

## 5. 단계 2 — 계산과 전송 주기 분리

**할 일**

- 게임 계산은 20 tick/s로 유지하고, 전체 상태 전송만 20Hz와 10Hz로 비교한다. 10Hz는 실험 후보이며 확정 사양이 아니다.
- 현재 클라이언트의 보간 유무와 동작을 확인한다. 전송 간격이 늘 때 이동이 끊기거나 표시 지연이 커지면 필요한 범위에서 보간을 조정하고 추가 지연을 기록한다.
- 공격·돌·짧은 효과가 두 전송 사이에서 발생하고 사라지는 경우를 검증한다. 필수 변화가 누락된다면 전송 조건을 보완하거나 20Hz를 유지한다.
- 입장·복구·퇴장·강퇴 등 중요한 변화의 즉시 전송 경로를 유지한다.
- 스냅샷 중복 생성·복사 비용도 측정한다. 같은 tick의 같은 내용을 반복 만드는 경우 실제 사용 범위에서만 줄인다.

**완료 기준**

- 동일 입력 조건의 송신량·CPU·tick 밀림과 실제 화면 동작을 비교한 기록이 있다.
- 전송 주기 변화가 이동 속도·쿨다운·충돌·피격 결과를 바꾸지 않는다.
- 시각적 품질과 지연을 확인한 값만 채택한다. 문제가 있으면 20Hz로 되돌릴 수 있다.

## 6. 단계 3 — 인증 조회 줄이기

2026-11-05 구현·로컬 검증을 마쳤고 [실행 기록](server-cost-stage3.md)에 정책과 전후 측정을 남겼다. 장치 폐기 반영 지연은 최대 약 1초로 확정했다. 6인 3개 방 활동의 인증 조회는 215.78/s에서 0.97/s로 줄었다. Windows 실기기 확인 전이라 단계 완료는 보류한다.

**할 일**

- JWT 검증 결과에서 얻은 장치 ID·만료 시간을 연결 컨텍스트로 관리하고, 재접속에는 다시 인증한다.
- 명령마다 필요한 방 멤버십·역할·sequence·입력 빈도 검증은 유지한다.
- 우선 현재 매초 수행하는 장치 상태 확인을 묶음 조회하고, 같은 확인을 명령마다 반복하지 않는 방법을 검토한다. 명령 처리와 차단 갱신이 동시에 일어날 때의 정책도 정의한다.
- 토큰 만료는 DB 재조회와 분리해 처리한다. 인증 캐시·연결 컨텍스트는 만료·로그아웃·종료 때 정리한다.
- 현재보다 장치 폐기 반영이 늦어지는 설계는 자동 채택하지 않는다. 허용 지연을 명시하고 정책을 확정한 후 적용한다. DB 장애 때의 명령 허용·차단 동작도 정한다.

**완료 기준**

- 입력 빈도가 늘 때 인증 DB 조회가 같은 비율로 증가하지 않는 것을 측정으로 확인한다.
- 토큰 만료, 장치 폐기, 방 퇴장·강퇴, 재연결, DB 장애 경로가 명세대로 동작한다.
- 인증 실패나 권한 변경을 우회하는 경로가 없고, 연결 종료 후 관련 자원이 남지 않는다.

## 7. 단계 4 — 단일 서버 제한 베타

**할 일**

- NestJS·PostgreSQL·HTTPS/WSS 프록시를 한 서버에 두는 구성을 운영 후보로 비교한다. DB 관리 부담과 백업 비용까지 포함해 선택한다.
- [기존 배포 준비 문서](m4-deployment.md)를 기준으로 운영 구성을 준비한다. 개발용 `compose.yaml`을 그대로 운영 설정으로 사용하지 않는다.
- 실측으로 서버 크기와 동시 방·연결 상한을 정한다. 한도를 넘는 신규 입장은 안전한 안내와 함께 제한하고, 기존 세션을 갑자기 끊지 않는다.
- 예산 알림과 입장 제한은 별도로 설계한다. 알림만으로 지출 상한이 보장된다고 가정하지 않는다.
- DB 외부 접근 제한, 서버 밖 백업과 복구, 로그 보관·회전, 서버 교체와 이전 버전 복귀 절차를 준비한다.
- 공개 라이선스, 에셋·폰트·의존성의 배포 가능 범위, 설치·자체 운영 문서, 배포본의 서명·갱신 방침을 정리한다. 라이선스 선택과 관련 비용은 TBD다.
- 실제 서버·DB 대상, 견적, 변경 결과와 복구 절차를 제시한 뒤 승인을 받아 배포·운영 migration·서명·게시를 실행한다.

**완료 기준**

- 실제 PC 간 입장·6인 플레이·단절·종료·업데이트 호환을 확인한다. 웹 테스트 결과와 Windows 실기기 결과를 구분한다.
- 백업 복원과 서버 재시작 시 종료 안내·로컬 복귀를 확인한다. 메모리 월드가 재시작 후 유지된다고 안내하지 않는다.
- 베타 기간의 실제 청구·송신량·방 사용 시간·피크 부하가 기록된다. 공개 범위 확대는 비용과 여유 용량을 확인한 뒤 결정한다.

## 8. 단계 5 — 셀프호스팅을 사용자 기능으로 제공

**할 일**

- 공식 서버와 자체 서버를 선택하고 주소를 저장하는 최소 설정을 설계한다. 주소 오류·연결 실패·계약 버전 불일치·서버 변경 중 세션 종료를 안내한다.
- 서버 주소·장치 자격 증명·초대 링크를 서버별로 구분한다. 자체 서버에 공식 서버의 토큰을 보내지 않고, 서버 변경 시 이전 소켓·조회 캐시·방 상태를 정리한다.
- 초대 링크가 어떤 서버의 방인지 식별하는 계약을 정한다. 링크를 열었다는 이유만으로 신뢰하지 않은 서버에 기존 자격 증명을 전송하거나 자동으로 서버를 전환하지 않는다.
- Vite 빌드 시 주소 고정과 Tauri CSP를 함께 검토한다. 임의 origin 전체 허용 대신 필요한 연결 범위와 명시적인 서버 선택을 설계한다.
- 기존 Docker 이미지 기반의 자체 운영 예시와 설치·백업·업그레이드·복구 문서를 제공한다. 새 패키지나 공개 계약 변경이 필요하면 구체안을 별도 확정한다.

**완료 기준**

- 코드 수정·앱 재빌드 없이 자체 서버에 연결하고 공식 서버로 복귀할 수 있다.
- 서로 다른 서버의 링크·장치 ID·토큰이 섞이지 않는다.
- 새 운영자가 문서만으로 서버를 설치하고 백업에서 복원할 수 있다.

## 9. 단계 6 — 공식 호스팅 수익성 검증

**할 일**

- 로컬 사용·자체 서버·공식 호스팅의 제공 범위를 정리한다. 유료 공식 호스팅의 가치는 연결 편의·운영·백업·지원으로 검증한다.
- 베타 실측으로 방 사용 시간당 비용과 전체 고정비를 구한다. 무료 이용과 유료 이용의 비용을 모두 포함한다.
- 가격, 무료 제공량, 동시 이용 한도, 초과 사용 정책, 지원 범위, 결제 실패·해지 정책을 정한다. 실제 요금·결제 수수료를 확인하기 전에는 수익을 확정하지 않는다.
- 정해진 정책에 필요한 최소 결제·권한 관리만 별도 구현 계획으로 작성한다. 장치 인증만 있는 현재 구조에 구독 소유자를 연결하는 계정·복구 정책도 포함한다.

**완료 기준**

- 무료 사용량을 포함해 비용을 감당할 수 있는 시나리오와 손익분기 조건이 있다.
- 실제 유료 수요와 결제 전환을 확인한 뒤 운영 한도를 확대한다. 가입자 증가만으로 수익성을 판단하지 않는다.

## 10. 비용 계산과 중단 기준

```text
월 운영비 = 서버 + DB + 초과 송신 + 백업/저장 + 도메인/로그 등 운영비
방 사용 시간 = 각 방이 해당 상태로 유지된 시간의 합
월 송신량 = 상태별(측정 송신 bytes/s × 유지 시간 s)의 합
월 손익 = 결제 수수료 등을 제외한 매출 - 전체 운영비 - 기타 사업 비용
```

현재 기록을 적용한 단순 예시는 `3,089.52 × 20 × 6 × 3,600`으로, 6명이 계속 같은 크기의 전체 상태를 받으면 방 하나당 약 **1.33GB/시간**이다. GB는 10억 bytes 기준이며 통신 부가 데이터는 제외한다. 10Hz에서 크기·인원·기타 전송이 같다면 해당 정기 전송분은 약 절반이다. 실제 개선율이나 전체 청구액이 절반이라는 뜻은 아니다.

| 판단 시점 | 결정 |
| --- | --- |
| 최적화 후 비용과 여유 용량이 충분함 | 현재 구조를 유지하고 추가 최적화 중단 |
| 대기 방이 비용의 대부분임 | 유휴 전송·계산과 혼자 있는 방의 처리 개선 우선 |
| 실제 게임 송신량이 비용의 대부분임 | 전송 크기·빈도 추가 실험 또는 P2P 타당성 비교 |
| CPU·DB가 먼저 한계에 도달함 | 측정된 병목부터 해결하고 트래픽 대책과 구분 |
| 예산·부하 한도에 접근함 | 확정한 정책에 따라 신규 입장·공개 범위 제한 |

## 11. 조건부 후속 과제

### 혼자 있는 온라인 방의 로컬 처리

단계 1 이후에도 1인 방의 계산 비용이 크면 검토한다. 서버에는 방문 가능 여부를 유지하되 첫 방문자 입장 시 서버 권위 월드로 전환하고, 마지막 방문자 퇴장 후 로컬로 돌아가는 경계를 설계한다. 위치·쿨다운·남은 효과·입력 중복·동시 입장을 처리해야 한다. 기존 규칙과 달리 클라이언트 좌표를 서버의 권위 상태로 채택해야 한다면 계약·신뢰 경계 변경안을 먼저 확정한다.

### P2P 또는 호스트 PC 판정

단계 4의 실사용 결과에서 중앙 서버 비용이 지속적으로 부담될 때 별도 실험한다. 직접 연결 성공률, 중계 비율·트래픽·비용, 지연, Windows 배포본 호환, 호스트 종료·절전·부정 입력 영향을 중앙 서버 방식과 비교한다. 중앙 서버의 판정 책임을 호스트 PC로 옮기는 명세·규칙 변경이 필요하며 초기 최적화에 포함하지 않는다. 실제 비용 절감과 사용 품질이 확인된 경우에만 채택한다.

## 12. 구현 시 검증과 작업 단위

구현은 `측정 확장 → 유휴 전송 → 활성 전송 주기 → 인증 조회 → 베타 운영 준비 → 자체 서버 연결 → 과금 계획` 순서로 나눈다. 각 변경에서 같은 시나리오의 전후 수치를 남기고, 효과가 없거나 동작이 나빠지면 해당 변경을 되돌린다.

- 서버 변경: manifest에 등록된 `pnpm --filter @deskbrawl/server lint`, `format:check`, `typecheck`, `test`를 사용한다. 타입 검사 전 Prisma Client 준비 여부를 확인한다.
- 인증·방·실시간 변경: 격리 PostgreSQL에서 `pnpm --filter @deskbrawl/server test:integration`을 실행한다. [시뮬레이션](../apps/server/test/simulation.test.cjs), [실시간 통합](../apps/server/test/visits.integration.cjs), [6인 통합](../apps/server/test/m4.integration.cjs)의 위험 경로를 보완한다.
- 클라이언트·계약 변경: 해당 패키지의 타입 검사·테스트와 [방문 클라이언트 테스트](../apps/desktop/src/realtime/visitClient.test.ts)를 실행한다. Rust·CSP 변경에는 [검증 가이드](testing-guide.md)의 네이티브 검사와 Windows 실행 확인을 추가한다.
- 성능 검증: 기존 6인 측정과 새 상태별·다중 방 측정을 사용한다. 기준선 없이 절감률·최대 인원을 보고하지 않는다.
- 새 의존성·호환성을 깨는 계약 변경·운영 배포는 프로젝트 승인 규칙을 따른다. 준비·로컬 검증과 실제 배포를 구분한다.

최초 계획 작성에서는 문서 경로·내용 일관성만 확인했다. 이후 0단계 성능 측정과 검증은 [별도 실행 기록](server-cost-stage0.md)에 남긴다. 운영 배포는 실행하지 않았다.
