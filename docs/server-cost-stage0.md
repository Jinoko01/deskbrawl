# 서버 비용 0단계 — 기준선 측정

작성일: 2026-11-01 · 상태: 로컬 기준선·후보 공시요금 확인 완료 · 월 예산·운영 상한 미정

[로드맵](server-cost-roadmap.md)의 0단계 로컬 측정과 후보 비용 산정을 진행했다. 서버 최적화·운영 배포·0단계 전체 완료를 의미하지 않는다. 사용자에게 확인한 결과 예산·선호 사업자·지역은 정해지지 않았다. 최종 운영 견적·월 예산·운영 입장 상한은 **TBD**다.

## 측정 범위와 재현 조건

- 부하 생성기와 NestJS 서버는 서로 다른 Node 프로세스다. PostgreSQL은 기존 개발 DB와 분리한 로컬 Docker 컨테이너를 사용한다.
- DB 버전은 PostgreSQL 17.11(Debian)이다. 측정·통합 테스트 뒤 장치/방/초대 레코드가 모두 0개임을 확인하고 이번 작업의 전용 컨테이너를 중지했다. 기존 개발 DB 컨테이너는 계속 실행 중이다.
- Node 22.20.0, pnpm 10.34.7, 기존 manifest·lockfile의 의존성을 사용한다. 새 의존성을 추가하지 않았다.
- 서버·공유 프로토콜·게임 코어 원본은 Git `cdef8a2ce736ae76e2513193e7738bab7d250cff`와 동일하다. 계측은 새 테스트 스크립트에서만 적용했다. 장비는 Intel Core Ultra 9 185H, 논리 CPU 22개, RAM 63.50GiB, Windows 10.0.26200이다.
- 측정 대상은 1 → 2 → 3개 방, 방마다 혼자 대기 → 6인 대기 → 6인 활동이다. 방 수별 새 서버 프로세스를 실행하며, 각 서버의 빈 상태도 측정한다.
- 상태별 준비 3초를 제외하고 10초씩 3회 연속 측정한다. 반복 사이에 월드를 초기화하지 않는다. 활동 조건은 준비 구간에도 같은 입력을 사용한다.
- 각 참가자는 명목상 이동 입력 10회/초, 근접 공격과 돌 투척을 번갈아 1회/초, 채팅 1회/초를 전송한다. 실제 명령 수와 경과 시간은 원본에 기록한다. 1280×720 월드, 계산 주기 50ms를 유지한다. 이동 방향은 입력 10회마다 바뀐다.
- 실제 데스크톱 클라이언트의 갱신 timer는 50ms이며 이동 중에는 더 자주 입력할 수 있다. 이번 10Hz 입력은 기존 벤치마크에서 이어받은 고정 비교 조건이다. 실제 앱의 최대 입력 부하·사용자 분포를 재현한 결과로 해석하지 않는다.
- 마지막 3개 방에서는 활동 120초를 추가 관측하고 같은 연결에서 방 종료·재생성을 5회 반복한다. 각 방 수에서 방문자·호스트 재접속을 확인한다. 종료 후 65초 동안 방·멤버·HTTP 연결 정리와 메모리를 관측한다.
- 장치 등록 10회/분, 연결 인증 20회/분 제한을 우회하지 않는다. 등록·재접속 준비 대기는 측정 구간에서 제외한다.
- 클라이언트는 `health: true`로 현재 HP 필드를 받는다. 과거 M4 결과의 클라이언트 옵션·코드와 다르므로 과거 숫자와의 차이를 최적화 효과로 해석하지 않는다.

### 재실행

전용 로컬 테스트 DB에 기존 migration을 적용하고 서버를 빌드한 후 실행한다. `TEST_DATABASE_URL`은 localhost이며 DB 이름에 `test`가 있어야 한다. 생성한 장치와 방·초대만 실행 종료 시 정리한다. DB 전체 초기화는 하지 않는다.

```powershell
# 저장소 루트. 프로젝트의 Node 22 및 pnpm 10.34.7 사용.
$env:DATABASE_URL = '<격리된 로컬 PostgreSQL 테스트 DB URL>'
pnpm --filter @deskbrawl/server db:migrate
pnpm --filter @deskbrawl/server build
$env:TEST_DATABASE_URL = $env:DATABASE_URL
$env:COST_BENCH_DB_CONTAINER = '<해당 DB 전용 컨테이너 이름>'
$env:COST_BENCH_ROOMS = '1,2,3'
$env:COST_BENCH_PARTICIPANTS = '6'
$env:COST_BENCH_REPEATS = '3'
$env:COST_BENCH_WARMUP_MS = '3000'
$env:COST_BENCH_PHASE_MS = '10000'
$env:COST_BENCH_LONG_MS = '120000'
$env:COST_BENCH_CHURN_CYCLES = '5'
$env:COST_BENCH_OUTPUT = "$PWD/docs/measurements/server-cost-stage0-2026-11-01.json"
node apps/server/test/cost-benchmark.cjs
```

[벤치마크](../apps/server/test/cost-benchmark.cjs)는 방 수·참가자 수·반복 수·준비/측정/장기 구간을 환경 변수로 받는다. 기본값은 준비 5초, 측정 30초×3, 추가 활동 600초다. 이번 실행은 위 명령에 명시한 짧은 로컬 기준선이며, 수 시간·수일의 안정성을 검증하지 않는다. `COST_BENCH_DB_CONTAINER`를 생략하면 DB 지표는 `null`이며, 전용 컨테이너가 아닌 공유 DB를 지정하면 DB 부하 분리가 성립하지 않는다.

## 지표의 의미

| 지표 | 수집 방식과 해석 |
| --- | --- |
| 서버 CPU | 서버 프로세스 CPU 누적 시간 차이 / 실제 구간 시간. 100%는 논리 코어 하나이며 전체 PC CPU 사용률이 아니다. |
| 서버·부하 생성기 메모리 | 각각 별도 프로세스 RSS. 최대치는 100ms 간격 관측값이고 순간 최고를 보장하지 않는다. heapUsed도 원본에 남긴다. |
| DB CPU·메모리 | 전용 PostgreSQL 컨테이너의 cgroup v2 누적 CPU 및 memory.current. 메모리는 페이지 캐시를 포함하고 RSS와 다르다. 구간 전후 표본이며 관측 명령의 작은 부하도 포함한다. |
| 인증 조회 | `revokedAt`을 선택하는 Prisma `deviceIdentity.findUnique` 호출 횟수. 실제 인증 경로에서 센 논리 조회 시도이며 PostgreSQL SQL statement 수와 구분한다. |
| 방 step 시간 | 시뮬레이션 step을 감싼 실행 시간. 내부 snapshot 생성은 포함하고 Gateway 송신은 제외한다. |
| 스케줄러 실행·지연 | 25ms 스케줄러 callback 실행 시간과 `max(0, 실제 호출 간격 − 25ms)`. 전체 방 step·동기 송신 경로를 포함한다. 250ms 초과 간격 횟수도 기록한다. |
| 소켓 송신 bytes | 서버 HTTP 연결의 `net.Socket.bytesWritten` 증가량. WebSocket·Engine.IO·Socket.IO framing과 ack/heartbeat를 포함한다. IP/TCP 헤더·재전송·TLS·프록시·DB 트래픽은 제외한다. 사업자가 청구하는 egress와 동일하지 않다. |
| JSON bytes 추산 | 모든 참가자가 수신한 snapshot을 다시 JSON 직렬화한 UTF-8 크기의 합. 소켓 송신 측정과 별도로 기록한다. |
| 입력 ack RTT | 클라이언트 emit → 서버 수락 ack. 시뮬레이션 적용·화면 반응·인터넷 지연을 의미하지 않는다. |

측정 장비·OS·모든 구간 원본은 [JSON 결과](measurements/server-cost-stage0-2026-11-01.json)에 보관한다. 원본에는 토큰·장치 자격 증명·DB URL이 포함되지 않는다.

계측용 함수 wrapper, 100ms 표본 수집, 구간별 통계 계산의 비용이 포함된다. 이후 단계도 같은 계측을 사용해 비교한다. 수신 JSON은 별도 프로세스에서 집계하지만 같은 PC의 자원을 공유하므로 물리적으로 독립된 부하 생성 환경은 아니다.

## 비용 산정과 운영 결정

```text
상태별 월 송신 GB = 측정된 상태별 bytes/s × 월 사용 초 / 1,000,000,000
전체 월 송신량 = 모든 방의 상태별 월 송신량 합계
월 비용 = 컴퓨팅 + DB + max(0, 청구 송신량 − 포함 송신량) × 초과 단가
        + 백업/스토리지 + 로그 + 도메인 등
```

실측 소켓 송신에 운영 TLS·프록시·IP overhead와 사업자 과금 방식을 반영해야 최종 청구 송신량을 산정할 수 있다. DB를 같은 서버에 두면 컴퓨팅·메모리·디스크·백업에 포함하고 관리형 DB를 별도로 더하지 않는다. GB와 GiB, 월 사용 시간, 세금·통화도 견적 단위와 맞춘다.

VM·객체 스토리지·스냅샷 금액은 [AWS Lightsail 공식 요금](https://aws.amazon.com/ko/lightsail/pricing/), 서울 초과 OUT 단가와 IN/OUT 합산 규칙은 [공식 FAQ](https://aws.amazon.com/ko/lightsail/faq/)에 근거한다. 스냅샷 20GB와 로그의 로컬 보관은 이 문서의 예산 가정이며 실제 저장량·보관 정책은 미정이다. 백업 복구·로그 회전은 아직 구현·검증하지 않았다. 공식 표의 TB/GB 표기를 유지했고, 실제 청구 시 과금 단위와 계정별 조건을 재확인해야 한다.

예를 들어 6인 활동 방 1개가 730시간 유지될 때 관측 소켓 OUT은 약 1,488GB, 2개면 약 2,976GB다. 이는 3TB 번들 허용량에 가까우며, IN·운영 통신 overhead·다른 전송을 더하면 포함량을 넘을 수 있다. 포함 전송량을 단순히 동시 방 수로 나누어 운영 상한을 정하지 않는다. 두 후보 모두 Linux 서버 실측 전이므로 Windows 측정의 CPU·메모리 수치를 그대로 대입해 수용량을 확정할 수 없다.
