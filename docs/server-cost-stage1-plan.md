# 서버 비용 1단계 실행 계획 — 대기 중 반복 스냅샷 줄이기

작성일: 2026-11-03 · 상태: 2026-11-04 구현·로컬 검증 완료, Windows 실기기 확인 전 — [실행 기록](server-cost-stage1.md)

목표는 **계산을 50ms 고정 tick으로 유지하면서, 변화가 없는 온라인 방의 반복 스냅샷 송신을 줄이는 것**이다. 근거는 [비용 로드맵](server-cost-roadmap.md)과 [0단계 측정](server-cost-stage0.md)이다. 이번 작업은 계획 문서 작성이며 앱 코드·공유 계약을 변경하지 않는다.

## 1. 출발점과 범위

0단계에서 방 1개가 혼자 대기할 때 소켓 송신은 평균 20.39KB/s, 6인 대기는 378.50KB/s였다. 6인 대기 3개 방은 1,138.23KB/s였다. 모두 로컬 측정이며 운영 청구 트래픽·수용량과 구분한다. 월 예산과 운영 입장 상한은 여전히 TBD다. 이 미정 항목은 운영 결정에 남겨 두고, 확보한 로컬 기준선으로 1단계 구현과 비교를 준비한다.

| 이번 단계에 포함 | 후속 단계로 남길 것 |
| --- | --- |
| 동일 상태의 정기 송신 생략, 시간 효과·입력 sequence·멤버 변경 보존 | 유휴 방의 계산 중지, 혼자 있는 방의 로컬 판정 전환 |
| 새 입장·재접속의 전체 상태 제공, 긴 정지 뒤 보간 보정 | 활동 중 10Hz 전송 실험, 일반적인 보간 방식 재설계 |
| 구버전과 신버전이 섞인 방의 호환성 | 인증 조회 축소, Redis, delta·바이너리 프로토콜 |
| 같은 조건의 전후 측정과 원본 저장 | 서버 구매·운영 배포·요금제 확정 |

새 의존성과 DB migration은 필요하지 않은 설계를 우선한다. 기능 호환성을 깨는 계약 변경이 필요해지면 구현 전에 구체안을 따로 확정한다.

기존 문서의 불일치도 있다. `docs/README.md`의 불변 조건은 체력이 없다고 설명하지만 현재 프로토콜·게임 코어·렌더링에는 HP와 회복 처리가 있다. 1단계에서는 이 제품 규칙을 새로 결정하지 않고 현행 필드·판정의 누락 여부를 검증한다. 제품 명세와 코드의 정합성 확정은 별도 항목으로 남긴다.

`world.tick`만 제외하고 JSON을 비교하는 방식만으로는 충분하지 않다. 예를 들어 공격의 `lastAction`과 기절 종료 tick 값은 그대로여도 현재 tick이 경계를 넘으면 화면 모션이 달라진다. 이동 종료 직후에는 좌표가 같은 후속 스냅샷이 있어야 `walk`가 `idle`로 바뀌는 점도 고려한다.

## 3. 채택할 구현 방향

### 3.1 지원을 명시한 연결에 우선 적용

구버전의 보간 동작을 보호하기 위해 **선택적 handshake 필드 `idleSnapshots: true`를 보내는 연결에만** 유휴 송신 생략을 적용하는 안을 사용한다. 이 이름은 이번 계획의 계약 제안이며 아직 구현된 기능이 아니다.

- 해당 필드가 없거나 `true`가 아닌 연결은 기존 정기 송신을 유지한다. 기존 `health` 옵션과 독립적으로 처리한다.
- 새 클라이언트는 보간 보정이 구현·검증된 뒤에만 이 필드를 전송한다. 구서버가 이 옵션을 무시해 정기 송신을 계속해도 정상 동작해야 한다.
- 기존 프로토콜 version, 이벤트 이름, snapshot·ack payload는 유지한다. 공유 프로토콜에는 선택적 capability의 의미와 검증을 최소 범위로 정의한다.
- `server:features`의 기존 strict 계약에 새 필드를 무조건 넣지 않는다. 구버전이 이벤트 전체를 거부해 WORK 드래그 기능까지 잃는 경로를 피한다.
- 혼합 방에서는 구버전 연결에 정기 송신을 계속하고, 지원 연결에만 생략한다. 구버전이 남아 있으면 방 전체 송신량·생성 비용의 감소가 제한된다는 점을 결과에 적는다.

### 3.2 송신 여부 판단

첫 구현은 Gateway의 송신 경계에 제한한다. 비교 대상은 클라이언트에 전달되는 현재 전체 상태를 기준으로 하되, 자동 증가하는 `world.tick`만 변화 판정에서 제외한다. 플레이어 전체 필드, HP, 위치·방향, 투사체·효과, 채팅, 멤버, `lastProcessedSeq` 등은 보존한다. 건강 상태 협상에 따른 HP 제거 등 기존 연결별 변환도 유지한다.

최대 6인 방의 작은 상태이므로 처음에는 tick을 제외한 상태의 직렬화 결과를 비교하는 단순한 방식을 우선한다. 별도 hash 라이브러리·전역 revision 체계·변경 추적 프레임워크는 도입하지 않는다. 비교 비용은 CPU·tick 측정에 포함하며, 정적 상태를 우연히 바꾸는 필드가 있는지 테스트한다.

| 조건 | 지원 연결에 대한 처리 |
| --- | --- |
| 직전 전송과 비교해 의미 있는 상태 변경 | 전체 스냅샷 송신 |
| 이동·투사체·넉백·기절·공격 모션·쿨다운·무적·효과가 진행 중 | 50ms tick마다 기존 전송 유지 |
| 채팅이 남아 있음 | 5초 fade·8초 제거가 보존되도록 기존 전송 유지 |
| 시간 효과가 끝나는 경계, 이동이 멈춘 뒤 정지 표시 확정 | 마무리 스냅샷 송신 후 유휴 판정 |
| 입력은 수락됐지만 위치가 그대로임 | `lastProcessedSeq`가 적용되면 송신. 벽 이동·0벡터 입력도 포함 |
| 위 조건 없이 tick만 증가 | 정기 스냅샷 송신 생략 |

시간 진행 판정에는 현재 서버의 종료 tick과 클라이언트 표시 구간을 함께 사용한다. 현재 공격 표시 구간은 근접 400ms·투척 300ms다. 기존 `lastAction`·`lastHitTick` 같은 이력 필드가 남아 있다는 이유만으로 영원히 활동 상태가 되지 않도록 **종료 시점과 현재 tick의 관계**로 판정한다. HP 0 상태의 회복도 기존 서버 판정을 따른다.

비교용 보관값은 방 객체 수명에 묶인 Gateway 소유 상태로 둔다. `WeakMap` 등으로 방 제거 후 참조가 남지 않게 하고, world 교체 시 이전 값과 비교하지 않는다. mutable snapshot 객체의 참조만 보관하지 않는다. 강제 송신 후에도 비교 기준을 갱신한다.

채팅 만료·단절 유예·매초 인증 확인·Socket.IO heartbeat는 송신 생략 여부와 독립적으로 계속 실행한다. 현재 `step()`과 Gateway의 중복 snapshot 생성 제거는 1단계의 필수 변경으로 삼지 않는다. 먼저 송신 절감과 회귀 여부를 확인한다.

### 3.3 중요한 이벤트는 즉시 반영

`room:host`, `visit:join`, `visit:resume`, 프로필 변경, 명시적 퇴장, 강퇴·전체 방문자 정리, 집중 모드 변경은 기존 전체 스냅샷·프로필·종료 이벤트 경로를 유지한다. 같은 tick의 멤버 변경도 허용한다.

대기 중 전송이 끊겨도 새 입장·재접속은 캐시된 옛 tick이 아닌 현재 전체 스냅샷을 받는다. transport disconnect가 채팅을 없애거나 입력을 취소하면 다음 정상 tick까지 반영하고, 만료에 의한 실제 퇴장·호스트 방 종료도 기존 종료 안내를 유지한다. 재접속 시 토큰 교체와 이전 visit 입력 거부는 그대로 검증한다.

### 3.4 긴 정지 뒤 화면 복귀

`createSnapshotView()`에서 정상 20Hz 입력의 보간은 유지하되, 스냅샷 tick 간격이 길어져도 위치 보간 시간을 현재 한 tick인 **최대 50ms로 제한**하는 안을 먼저 검증한다. 긴 무수신 시간 전체를 보간 길이로 사용하지 않는다. 서버 tick 자체를 임의로 바꾸거나 클라이언트가 전투·위치를 외삽하지 않는다.

첫 이동·첫 WORK 드래그, 같은 tick의 멤버 변경, 새 world, 재접속, 패킷 지연 후 복귀를 각각 테스트한다. 50ms 제한은 1단계의 20Hz 전송 전제에 따른 것이며, 2단계의 10Hz 실험에서는 다시 검토한다. 현재의 프레임 예약·dispose 동작도 보존한다.

| 검증 | 통과 조건 |

| 채팅 | 갱신·빈 문자열 제거·5초 fade·8초 만료·disconnect 제거·집중 모드 제거 보존 |

| 재접속 | 최신 전체 상태와 동일 world 복구, 새 visit/token 발급, 이전 입력 거부 |
| 호환 조합 | 구클라→신서버, 신클라→구서버, 신클라→신서버, 혼합 방에서 각 정책 유지 |

“전송이 오지 않음” 검증은 무한 대기 대신 범위가 정해진 수신 건수 관찰로 수행한다. 단위 검증은 clock·tick을 명시적으로 진행하고, Socket.IO 통합 검증에서는 실제 heartbeat를 멈추는 전역 fake timer를 사용하지 않는다. snapshot을 연결 확인용 heartbeat로 기다리는 기존 fixture가 있다면 실제 검증 의도에 맞게 보완한다.

## 6. 성능 비교 계획

- 0단계의 2026-11-01 결과는 참고값으로 보존한다. 인과 비교에는 이번 구현 직전·직후의 새 결과를 사용한다. 장비·Node·DB·입력·클라이언트 옵션·계측 코드를 맞추고 제품 소스 hash를 남긴다.
- 벤치마크의 신규 연결 옵션은 `COST_BENCH_IDLE_SNAPSHOTS=1`로 제안한다. 변경 전 서버에도 같은 옵션을 보내되 기존 서버가 이를 무시하는지 확인해 동일 입력 조건을 맞춘다. 변경 후에는 옵션 없는 연결과 혼합 방도 별도로 검사한다.
- 기본 비교는 1·2·3개 방, 방당 1인·6인 대기·6인 활동, 상태별 준비 3초 제외 후 10초×3회, 18명 추가 활동 120초, 방 재생성 5회, 종료 후 65초 관측을 유지한다. 입력은 기존 명목 10Hz, 행동·채팅 각 1Hz 조건을 유지한다.
- 별도 회귀 시나리오는 장시간 대기 후 첫 이동·WORK 드래그·재접속이다. 긴 대기 연결 검증은 실제 Engine.IO heartbeat 설정의 한 주기 이상을 포함하고, 사용한 실제 지속 시간을 기록한다. 기존 앱의 50ms 입력 timer 부하는 별도 조건으로 분리한다.
- 서버·부하 생성기·DB CPU/메모리, 인증 조회, step·스케줄러 실행·밀림, 소켓 bytesWritten, JSON bytes, 입력 ack RTT와 재접속을 다시 수집한다. 특히 **첫 스냅샷의 적용 sequence 확인 시간**과 **실제 화면 반응**을 ack RTT와 구분한다.
- 대기 송신 감소율은 `(변경 전 bytes/s − 변경 후 bytes/s) / 변경 전 bytes/s × 100`으로 상태·방 수별 기록한다. heartbeat·인증·ack 때문에 전체 송신량이 0이 된다고 가정하지 않는다.
- 활동 전송은 20Hz 유지가 기준이다. CPU·ack 지연·tick 밀림의 반복 악화가 보이면 원인을 확인해 채택 여부를 판단한다. 목표 절감률·운영 지연 SLO·월 비용은 실측과 운영 정책 확정 전까지 TBD다.

## 7. 실행할 검사와 완료 조건

구현 시 실제 등록 스크립트와 Prisma Client 준비 상태를 다시 확인한 뒤 실행한다.

```powershell
pnpm --filter @deskbrawl/server build
pnpm --filter @deskbrawl/server lint:fix
pnpm --filter @deskbrawl/server format:check
pnpm --filter @deskbrawl/server typecheck
pnpm --filter @deskbrawl/server test
# 격리된 PostgreSQL과 TEST_DATABASE_URL 준비 후
pnpm --filter @deskbrawl/server test:integration
pnpm --filter @deskbrawl/protocol lint
pnpm --filter @deskbrawl/protocol typecheck
pnpm --filter @deskbrawl/protocol test
pnpm --filter @deskbrawl/desktop lint
pnpm --filter @deskbrawl/desktop typecheck
pnpm --filter @deskbrawl/desktop test -- src/realtime/visitClient.test.ts src/game/networkScene.test.ts
pnpm --filter @deskbrawl/desktop build
```

0단계에서는 전체 서버 포맷 검사가 기존 Prisma 스킬 Markdown 63개 문제로 실패했다. 구현 시 현재 상태를 다시 확인하고, 관련 없는 파일을 일괄 수정하거나 검사를 제외해 통과시키지 않는다. 새 변경 파일의 검사는 별도로 통과시키고 전체 검사 결과도 그대로 보고한다.

완료는 다음을 모두 충족한 상태로 정의한다.

1. 새 지원 연결의 완전 유휴 정기 스냅샷이 생략되고, 같은 대기 조건의 실제 소켓 송신량이 기준선보다 감소했다.
2. 위 기능 검증표가 통과하고, 활동 상태의 서버 판정·시간 진행·전송 주기가 보존됐다.
3. 구버전 호환성, 재접속·인증·종료, Windows 화면 동작을 확인한 범위를 근거와 함께 기록했다. 미확인 항목이 있으면 단계 완료를 보류한다.
4. 전후 원본·조건·송신 감소율·CPU/메모리·지연 결과와 남은 제한을 문서 및 Obsidian에 남겼다.

문제가 생기면 서버의 capability 경로에서 생략 판단을 끄고 기존 정기 송신으로 복귀한다. 새 클라이언트는 기존 정기 송신도 처리하므로 서버 판정·DB 데이터를 되돌릴 필요가 없는 구성을 유지한다. 이 계획에서 실제 배포나 운영 rollback을 실행하는 것은 아니다.

## 8. 이번 계획 작성에서 확인한 것

로드맵·0단계 결과, 서버 tick·Gateway·세션 수명, 클라이언트 보간·연결 처리, 관련 기존 테스트와 manifest를 읽고 계획을 작성했다. 문서 링크와 경로·내용 일관성만 검사한다. 앱 검사·성능 재측정·네이티브 실행은 구현 단계의 작업이며 이번에는 실행하지 않았다. 현재 환경에 `wmux` 명령이 없어 markdown pane은 열지 못하며, 저장소 문서와 기존 Obsidian 프로젝트에 계획을 저장한다.
