# 풀스택 코드 품질

기존 프론트엔드 가이드의 가독성·예측 가능성·응집도·결합도 기준을 데스크톱·서버·공유 프로토콜까지 확장한다. 기준이 충돌하면 변경 맥락에 맞게 판단하고 이유를 짧게 남긴다.

## 가독성

- 함수·컴포넌트가 무엇을 하는지 이름과 입력·출력으로 드러낸다. 복잡한 조건은 `canJoinRoom`, `isExpiredInvite`처럼 의미 있는 이름으로 표현한다.
- 시간·좌표·틱·sequence는 단위와 기준을 드러낸다. ms와 s, 화면 좌표와 월드 좌표를 암묵적으로 섞지 않는다.
- 중첩 조건보다 명확한 상태 전이와 조기 반환을 우선한다. 짧은 코드를 만들기 위해 도메인 규칙을 숨기지 않는다.
- 요청 수신 → 검증 → 인증·인가 → 상태 변경 → 응답의 흐름이 추적 가능해야 한다.

## 예측 가능성

- 같은 역할의 API·명령은 같은 성공·실패 표현을 사용한다. 조회 함수가 몰래 상태를 변경하거나 timer를 시작하지 않는다.
- ack가 무엇을 확인하는지 명확히 한다. 전송 성공·서버 수락·게임 적용·DB 저장은 서로 다른 결과다.
- REST·Socket.IO·IPC의 타입이 같아도 런타임 신뢰 경계에서 검증한다.
- 비동기 작업의 취소·중복·재시도·종료 동작을 명시한다. timeout을 서버 실행 취소로 간주하지 않는다.

## 응집도

- 함께 바뀌는 schema·handler·도메인 규칙·테스트를 찾기 쉽게 배치한다. 실제 wire 계약은 공유 프로토콜 한곳에서 관리한다.
- 게임 규칙은 서버 시뮬레이션에, 장면 표현은 PixiJS 런타임에, OS 처리는 Rust 경계에 모은다.
- 값 하나에 수정 가능한 원본을 여러 개 두지 않는다. HUD는 snapshot에서 필요한 값만 선택한다.
- 새 폴더 구조를 강요하지 말고 기존 도메인 경계를 개선한다.

## 결합도

- 공유 프로토콜은 앱·서버 구현을 import하지 않는다. DB 타입과 네이티브 타입이 UI 전체로 전파되지 않게 한다.
- 시뮬레이션은 Socket.IO·Prisma·실제 시계 없이 step 단위로 검사할 수 있게 한다.
- 하나의 구현을 위해 interface·repository·factory를 기계적으로 만들지 않는다. 프레임워크의 기본 DI·검증·트랜잭션을 먼저 사용한다.
- 공통화는 실제 같은 책임에 적용한다. 비슷하게 보이는 UI나 DTO를 무조건 하나로 합치지 않는다.

## 변경 전후 점검

1. 호출자와 실제 실패 경로를 확인한다.
2. 상태 소유권·계약·인가·생명주기에 미치는 영향을 확인한다.
3. 요청 범위의 가장 단순한 변경을 적용한다.
4. 핵심 동작과 위험에 맞는 검증을 수행한다.
5. 실행 결과와 남은 제약을 사실대로 보고한다.
